# SDK Review: remaining concrete defects

Scope note: this only covers remaining SDK/runtime defects after the recent fixes. I am intentionally not counting the separate root switch/branch restore work that is already in progress.

1. **Root runtime API-key overrides still do not propagate into child runtimes.** `createDriverFactory()` builds a fresh `ModelRuntime` from disk and only re-registers providers/configs from the root registry (`src/runtime.ts:54-65`). That preserves custom providers, but not runtime-only API-key overrides; Pi 0.99.2 keeps those in a `RuntimeCredentials` overlay (`node_modules/@earendil-works/pi-coding-agent/dist/core/runtime-credentials.js:2-37`). The public registry already exposes enough surface to bridge this (`.../model-registry.js:63-65,98-108`). Current coverage only exercises a static `registerProvider({ apiKey })` config, not `setRuntimeApiKey()`-style auth (`tests/runtime.test.ts:35-53`). **Smallest remedy:** if `ctx.modelRegistry.getProviderAuthStatus(provider).source === "runtime"`, copy `await ctx.modelRegistry.getApiKeyForProvider(provider)` into the child runtime via `runtime.setRuntimeApiKey()` before model lookup, plus one focused regression.

2. **Paused-session queued input is not durable across dispose/reopen.** On pause, queued steering/follow-up input is stripped out of the SDK queue and parked only in the driver closure (`src/runtime.ts:134-145,173-175`). Reopen reconstructs state only from the JSONL transcript (`src/runtime.ts:29-39,75-79`), so any parked messages disappear if the driver is disposed before resume. The current pause test queues a steer before pause, but never asserts it survives reopen (`tests/runtime.test.ts:132-149`). **Smallest remedy:** persist paused queued input (e.g. a private custom entry), or reframe pause so queued resume input is appended durably instead of living only in `parked`.

3. **`sendUpdate()` is still memory-only at the exact times retained sessions matter most.** The driver sends mailbox/progress messages with `deliverAs: "nextTurn"` (`src/runtime.ts:204-208`). In Pi 0.99.2 that is an in-memory pending-next-turn queue, not a persisted session entry, so updates sent while a child is paused/running are lost on dispose/reload before the next prompt. The new test only proves a pre-prompt update survives because it gets consumed into the first turn before pause; it does not cover updates sent after the run has started or while already paused (`tests/runtime.test.ts:129-145`). **Smallest remedy:** for non-turning child updates, use a durable custom message path (`triggerTurn: false` without `deliverAs: "nextTurn"`) or explicitly persist deferred updates.

4. **Saved-thread durability still trusts `sessionFile` paths before the file necessarily exists.** `ThreadManager.saved()` omits the inherited-context fallback as soon as a driver reports any `sessionFile` path (`src/manager.ts:49-55,227-230`). But the SDK exposes that path before the test’s first prompt (`tests/runtime.test.ts:79-80`), and restore later requires `realpath(options.sessionFile)` to succeed (`src/runtime.ts:29-39`). That leaves a startup/shutdown race where a thread can be persisted with a path that was never materialized on disk, then fail restore. **Smallest remedy:** only treat `sessionFile` as durable once the file exists, otherwise persist `inherited` and reopen as a fresh in-memory transcript.
